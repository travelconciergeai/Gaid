Documento 06 — Real Data Ready Front

Props Reference — Real Data Ready

A nova aba Gaid Real Data Ready.html com o front inteiro preparado para o backend: componentes presenter puros, dados por props, os 4 estados em toda tela, e nenhum dado falso em modo real. Este doc lista o que cada componente espera receber.

Arquivo · Gaid Real Data Ready.html Fonte da verdade · Trip Context · só activeTripId

00Como ler & como testar

Todo componente segue o mesmo padrão: dado entra por props (já resolvido da camada de dados), intenção sai por callback (onApply, onOpen…). Nenhum componente faz fetch, inventa valor ou lê mock. Quando um campo não existe, renderiza "A definir" — nunca um valor fabricado.

A barra escura no topo do app é o painel de handoff:

ControleO que faz
Dados · Real (vazio)Modo que vai pro ar. Backend ainda não plugado → tudo vazio. Zero dado falso.
Dados · AmostraServe fixtures através da camada de dados (nunca dentro de componentes) para revisar a UI premium.
Estado · Auto/Loading/Empty/Error/SuccessForça qualquer tela em qualquer um dos 4 estados — para inspeção e QA.

01Camada de dados (o seam)

Três arquivos isolam de onde o dado vem. Telas só conhecem o tripApi.

MóduloPapel

rdr/data/dataMode.jsxDATA_MODE (real ↔ sample) + harness de force-state, persistido.

A Trip que o front consome (igual ao contrato do Doc 01) Trip { id, status, destination, city, country, dates:{start,end}, travelers:[{kind}], budget, preferences:{styles,hotel,flight}, hotel, flights:[], tours:[], days:[] } // Ausências esperadas → tratadas, não inventadas: budget: null → "A definir" dates: null → "A definir" hotel: null → slot "Adicionar hotel" flights: [] → slot "Adicionar voo" tours: [] → slot "Adicionar passeio"

04GuidedWizard & OnboardingStep

Em rdr/components/wizard.jsx. Presenters controlados — o container detém answers/stepIndex e chama tripApi.createTrip. O wizard não cria a Trip nem adivinha destino/datas.

Destino resolve para id (ADR-09)

O passo destination usa resolveDestination(texto) → DestinationId sobre uma lista curada. Sem correspondência, mostra "não encontrei" — nunca chuta um destino. É o que impede "Porto→Paris".

06Regras de ouro (o que NÃO acontece)

Garantias do Real Data Ready
  • Nenhum mockData dentro de componentes. Fixtures só no tripApi, atrás do seam.
  • Nenhum texto hardcoded fingindo dado real. Ausência → "A definir" ou AddSlot.
  • Nenhum componente inventa destino, datas, hotel, voo, passeio, orçamento ou viajantes.
  • Em modo real, tudo vem vazio — é o estado honesto enquanto não há backend.
  • Trip é a fonte única; ActiveTripContext guarda só activeTripId.
  • Todo componente data-driven desenha loading / empty / error / success.

07Onde o backend pluga (semana que vem)

Um arquivo. Trocar cada corpo de método do tripApi por uma chamada real — as assinaturas e os formatos de retorno são o contrato e não mudam, então nenhuma tela ou componente é tocado.

rdr/data/tripApi.jsx — antes → depois // HOJE (sem backend) async listTrips(_p, mode) { return mode === 'sample' ? SAMPLE.trips : []; } // SEMANA QUE VEM (backend plugado) — mesma assinatura, mesmo retorno async listTrips() { const r = await fetch('/api/v1/trips'); return (await r.json()).data; // já no formato Trip[] }
