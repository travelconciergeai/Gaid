Gaid API Contracts V1

Os payloads oficiais que frontend e backend compartilham. Mesma forma dos dois lados, mesmos ids do Documento 01. Se o contrato muda, muda aqui primeiro — nunca em um lado só.

Base · /api/v1 Formato · JSON · ids canônicos Concorrência · version + If-Match

00Convenções (envelope, erro, concorrência)

Toda resposta usa o mesmo envelope. Toda escrita carrega versão. Toda mutação que “aplica” algo é idempotente.

Envelope de resposta — sucesso e erro // Sucesso { "data": T, // o recurso ou lista "meta": { "requestId": string, "page"?: Page } } // Erro — SEMPRE esta forma, nunca HTML/string solta { "error": { "code": string, // "validation_failed" | "version_conflict" | "not_found" … "message": string, // legível, pt-BR "fields"?: FieldError[], "requestId": string } }
Concorrência & idempotência — headers If-Match: "<trip.version>" // toda escrita em Trip; 409 se desatualizado Idempotency-Key: "<uuid>" // toda mutação "apply"/create; evita duplicar
Por que isso resolve “estados conflitantes”

Se duas origens (usuário e expert, ou duas abas) tentarem escrever sobre a mesma version, a segunda recebe 409 version_conflict e re-sincroniza — em vez de sobrescrever silenciosamente. Idempotency-Key garante que “aplicar hotel” duas vezes não crie duas reservas.

Decisão recomendadaADR-07 · Contratos

O contrato é a fonte compartilhada — front e back derivam dele, nunca o contrário

Decisão
Os payloads deste documento (envelope, entidades por id, version, Idempotency-Key) são a fonte única do contrato. Tipos de frontend e backend são derivados do mesmo schema; mudança de contrato muda aqui primeiro.
Justificativa
Contratos divergentes entre os lados são a origem de “dados inventados” e quebras na integração. Um schema compartilhado garante que os dois lados falem exatamente a mesma língua.
Riscos
Versionar o contrato exige disciplina (breaking changes precisam de /v2); requer um lugar único onde o schema vive.
Não deve acontecer
Frontend “ajustar” o shape no cliente; backend mudar campo sem atualizar o contrato; erro retornar HTML/string em vez do envelope; escrita sem If-Match.
Impacto · Frontend
Consumir tipos gerados do schema; tratar 409 com re-sync; enviar Idempotency-Key em create/apply; nunca recalcular preço/milhas.
Impacto · Backend
Validar todo request contra o schema; sempre devolver o recurso inteiro no envelope; impor version/idempotência; cálculos (preço, milhas, progresso) prontos.
Impacto · Codex
Gerar tipos a partir do schema (single source); criar um cliente de API tipado; testes de contrato que falham se request/response divergir do payload definido aqui.

01Buscar hotéis · voos · passeios

Buscas são read-only e retornam entidades de catálogo já normalizadas (ids canônicos de cidade/aeroporto). O cliente nunca recalcula preço/milhas.

POST /search/hotels // request { "cityId": DestinationId, "checkIn": ISODate, "checkOut": ISODate, "guests": { "adults": number, "children": number }, "filters"?: { "style"?: string[], "maxPrice"?: number }, "page"?: Page } // response.data Hotel[] // cada item conforme schema Hotel (Doc 01)
POST /search/flights // request { "fromAirportId": AirportId, "toAirportId": AirportId, "depart": ISODate, "return"?: ISODate, "pax": { "adults": number, "children": number, "infants": number }, "cabin"?: string, "milesProgram"?: string } // response.data Flight[] // preço e milhas JÁ calculados pelo backend
POST /search/tours // request { "cityId": DestinationId, "date"?: ISODate, "filters"?: { "category"?: string[], "maxPrice"?: number }, "page"?: Page } // response.data Tour[]

02Criar roteiro

Cria a Trip como draft a partir das respostas do wizard. Retorna a Trip com id real e version: 1. A geração de dias pela IA é um passo separado (assíncrono), com seu próprio status.

POST /trips · (Idempotency-Key) // request — intenção do wizard, destinos por id { "source": "wizard", "destinations": DestinationId[], "dateRange"?: { "start": ISODate, "end": ISODate }, "travelers": Traveler[], "budget"?: Money, "preferences": { "styles": string[], "hotel": string[], "flight": string[] } } // response.data — Trip status:"draft", version:1, days:[] Trip
POST /trips/{tripId}/generate · geração de roteiro pela IA // request { "regenerate"?: boolean, "keepLocked": true } // response.data — Trip com days preenchidos; itens locked preservados Trip // version incrementada
Fronteira da IA

A IA roda no servidor e produz um patch validado contra schema + ids existentes antes de persistir. Itens com locked: true nunca são tocados por generate. É aqui que “dados inventados” são barrados — não no cliente.

03Atualizar roteiro

Edições granulares por patch. Sempre com If-Match: version. Retorna a Trip nova com version incrementada — o cliente troca o cache inteiro pela resposta (sem merge manual).

PATCH /trips/{tripId} · (If-Match: version) // request — operações atômicas sobre o itinerário { "ops": [ { "op": "addItem", "dayId": TripDayId, "item": ItemDraft }, { "op": "moveItem", "itemId": ItemId, "toDayId": TripDayId, "toSlot": Slot }, { "op": "updateItem", "itemId": ItemId, "patch": Partial<Item> }, { "op": "removeItem", "itemId": ItemId }, { "op": "setLock", "itemId": ItemId, "locked": boolean } ] } // response.data — Trip atualizada (nova version) Trip // 409 version_conflict → cliente refaz GET e reaplica

04Aplicar hotel · voo · passeio ao roteiro

“Aplicar” cria um BookingRef e amarra a entidade aos itens corretos do itinerário. Idempotente por Idempotency-Key.

POST /trips/{tripId}/apply · (If-Match + Idempotency-Key) // request — um destes por chamada { "refKind": "hotel", "refId": HotelId, "nights": { "checkIn": ISODate, "checkOut": ISODate } } { "refKind": "flight", "refId": FlightId, "dayId"?: TripDayId } { "refKind": "tour", "refId": TourId, "dayId": TripDayId, "slot": Slot } // response.data — Trip com novo BookingRef + itens marcados "booked" { "trip": Trip, "booking": BookingRef }
AçãoEfeito no itinerárioStatus do item
applyHotelcria/atualiza itens checkin nas noitesbooked
applyFlightinsere item flight no dia da partidabooked
applyTouranexa item tour ao dia/slotbooked
