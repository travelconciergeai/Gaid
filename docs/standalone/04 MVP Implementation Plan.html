Documento 04 — execução

Gaid MVP Implementation Plan V1

Traduz a arquitetura (Docs 01–03) no menor recorte que prova o loop central: criar uma viagem, buscar um hotel, aplicá-lo ao roteiro e ver tudo em Minhas Viagens — com a Trip como fonte única da verdade e sem mocks fabricando dados. Nada além disso entra agora.

Princípio · um loop completo > muitas features pela metade Verdade · Trip (servidor) ↔ TripStore (cliente) Sem · overengineering — ver §02

01Escopo do MVP

ItemO que entra
Trip = fonte da verdadeA entidade Trip (Doc 01, recorte mínimo) é a única representação de uma viagem. Persistida pela camada de dados.
TripStore (frontend)Um cache normalizado único + selectors + ações. Nenhuma tela guarda cópia de dados de viagem.
GuidedWizardColeta destino (por id), datas e travelers; cria a Trip como draft e a atualiza; define como ativa.

DATA_MODE realCamada de dados com seam único; modo real persistente, sem mocks fabricando viagens/hotéis.
Recorte da Trip para o MVP

Só os campos que o loop exige: id, ownerId, title, status, destinations[], dateRange, travelers[], days[], bookings[], createdAt, updatedAt. days nasce derivado do dateRange (dias vazios) e ganha itens ao aplicar hotel. Campos como budget, expertId, coverRef, confidence, locked existem no modelo mas não são necessários agora.

02O que fica fora (explicitamente)

Adiado de propósito — não por esquecimento. Cada item entra depois reusando o mesmo padrão do hotel.

Voos
FlightCard, applyFlight — depois do hotel provar o padrão.
Passeios
TourCard, applyTour.
Experts
Atribuição e canal — fora do loop central.
Assinatura / planos
Billing não toca o loop de viagem.
Versionamento avançado / If-Match
Sem concorrência otimista agora (usuário único, sequencial).
Idempotency-Key
Sem chave de idempotência nesta fase.
Multi-dispositivo
Uma sessão, um cliente.
Edição colaborativa
Sem expert/co-edição simultânea.
Geração de roteiro por IA
Fora do recorte: dias vazios + itens via aplicar hotel já fecham o loop.
Dívida consciente (não esquecer)

A camada de dados deve ser desenhada para que version, If-Match e Idempotency-Key caibam depois sem reescrever o store — os endpoints já recebem/devolvem a Trip inteira, então adicionar os headers é incremento, não refatoração. É a única concessão que fazemos ao futuro.

03Ordem de implementação

Sequência pensada para que cada passo seja verificável isolado e nada dependa de algo ainda não construído (de baixo para cima: dados → store → telas).

Fase 0 — Fundação de dados

  1. Definir tipos declarativos do recorte MVP (Trip, TripDay, ItineraryItem, Hotel, Destination).
  2. Criar dados de referência de destinos (lista canônica pequena, com id).
  3. Criar o seam DATA_MODE e o cliente tripApi (modo real persistente).

Fase 1 — Verdade no cliente

  1. Implementar o TripStore (cache normalizado + selectors + ações).
  2. Implementar o ActiveTripContext (só id + selectors), reidratável.

Fase 2 — Criar e listar

  1. GuidedWizard → createTrip (draft) → define ativa.
  2. Minhas Viagens lendo só o TripStore (lista + estados vazio/loading).

Fase 3 — Hotel & roteiro

  1. Busca de hotéis via searchHotels → HotelCard (4 estados).
  2. Aplicar hotel → ação applyHotel → TripItinerary reflete o item.

Fase 4 — Corte dos mocks

  1. Remover qualquer leitura de mockData.trips / dataKey nos fluxos acima. DATA_MODE = real, ponta a ponta.

Aproveitando o que já existe

O account.jsx e os empty states já construídos são reaproveitados: o account vira a camada de sessão/usuário, e o TripStore assume os dados de viagem (hoje espalhados em mockData.trips + clones de tela). TripsScreen, WalletScreen etc. já lêem de um store — falta apontar a parte de viagens para o TripStore real.

DATA_MODE — o seam, sem mocks

Um único ponto decide a origem dos dados. No MVP existe só o modo real; o seam existe para que trocar a implementação (local persistido → backend HTTP) não toque em nenhuma tela.

data/dataMode — contrato do seam (declarativo) // Um enum, não um monte de ifs espalhados. DATA_MODE = "live" // MVP: única opção ativa // tripApi expõe SEMPRE o mesmo contrato, qualquer que seja o backing: tripApi = { createTrip(input): Trip, getTrip(id): Trip, listTrips(): TripSummary[], patchTrip(id, ops): Trip, searchHotels(q): Hotel[], applyHotel(id, hotelId, nights): { trip: Trip, booking: BookingRef } }
Regra: “sem mocks” significa

Proibido fabricar viagens a partir de mockData.disneyTrip et al. Permitido: dados de referência (lista de destinos, catálogo de hotéis de exemplo servidos através do tripApi como se viessem do backend). A diferença é que tudo passa pelo contrato — nada é montado direto na tela.

05Riscos

R1 — TripStore reabsorver responsabilidades demais

Tentação de jogar tudo (usuário, milhas, UI) no TripStore. Mitigação: TripStore só cuida de Trips; sessão/usuário fica no account; nada de estado de UI.

R2 — Clones de estado sobreviventes

PlanScreen/TripItinerary podem continuar clonando days “por hábito”. Mitigação: revisão dirigida + a regra de não ter useState com dados de viagem.

R3 — Seam vazar para as telas

Telas chamando persistência direta em vez do tripApi. Mitigação: toda I/O de viagem passa pelo store → tripApi; tela nunca importa a camada de persistência.

R4 — Quebrar telas fora do escopo

Wallet/Miles/Experts ainda em mock podem quebrar ao mexer na base. Mitigação: mantê-las intactas; o MVP só troca a origem das viagens.

R5 — Destinos canônicos incompletos

Wizard oferecer destino sem id correspondente. Mitigação: wizard só permite escolher da lista de referência; texto livre sem match é bloqueado/sinalizado.

06Critérios de aceite

Verificáveis e binários — passou ou não passou.

#Critério
A1Concluir o wizard cria uma Trip com id real e status: "draft", que aparece imediatamente em Minhas Viagens.
A2Minhas Viagens lê exclusivamente do TripStore — busca por mockData.trips retorna zero ocorrências no fluxo.
A3Buscar hotéis para o destino da Trip retorna resultados via tripApi.searchHotels e renderiza HotelCard nos 4 estados (loading/empty/success/error).
A4Aplicar um hotel cria um BookingRef e insere item(ns) checkin no TripItinerary — visível sem reload.
A5Sair e voltar à Trip (navegar entre telas) mostra o mesmo estado; nenhuma edição se perde (sem clones).
A6Recarregar a página reidrata a Trip ativa pela URL/sessão sem recriar dados.
A7Nenhum componente faz I/O direto: toda leitura/escrita de viagem passa por store → tripApi.
A8Lugares trafegam por DestinationId; em nenhum ponto do fluxo um destino é comparado/armazenado como string livre.
A9DATA_MODE = "live"; trocar a implementação do tripApi não exige alterar nenhuma tela.
Definição de pronto (MVP)

O loop Wizard → TripStore → Hotel → Aplicar → Minhas Viagens roda ponta a ponta, com A1–A9 verdes, sem nenhuma viagem ou hotel fabricado fora do tripApi. A partir daí, voos/passeios/experts entram clonando o padrão do hotel — sem novas decisões de arquitetura.
