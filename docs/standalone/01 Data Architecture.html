Gaid Data Architecture V1

A camada de dados que decide o que existe, quem manda e como a informação flui entre wizard, telas e backend. Tudo que vem depois — componentes e API — se apoia neste documento.

Status · proposta para aprovação Escopo · modelo, fonte da verdade, contexto ativo, ciclo de vida Regra de ouro · nenhum dado é inventado no cliente

00Diagnóstico da arquitetura atual

Os sintomas relatados — “Porto virando Paris”, dados inventados, estados conflitantes, regressões, contexto perdido entre telas, roteiros inconsistentes — não são bugs isolados de UI. São o sintoma clássico de uma única doença: não existe uma fonte única da verdade. Hoje a mesma viagem vive, simultaneamente, em quatro lugares que discordam entre si.

Risco 1 — múltiplas fontes da verdade

A viagem é montada a partir de um catálogo estático (mockData.trips → dataKey → mockData.disneyTrip…), enquanto o que o usuário possui vive na account store, enquanto a tela de planejamento mantém a sua própria cópia. Três representações da “mesma” viagem, nenhuma autoritativa.

Risco 2 — estado duplicado e clonado

A tela de roteiro faz JSON.parse(JSON.stringify(trip.days)) para o estado local e re-semeia o chat a partir de mockData.chatSeed sempre que o tripId muda. Edições passam a existir só na memória do componente; ao trocar de tela ou regenerar, o clone é descartado e a viagem “volta no tempo”. É exatamente o contexto se perdendo e a regressão.

Risco 3 — lugares como texto livre

Destinos e cidades trafegam como strings (“Porto”, “Lisboa”, “warm”) acopladas a seeds de imagem e a chaves posicionais. Sem um identificador canônico, qualquer regeneração ou recálculo pode trocar “Porto” por “Paris” sem nada detectar o erro — o sistema não sabe que são entidades diferentes.

Risco 4 — IA sem fronteira de dados

A geração de roteiro produz objetos livres. Sem um schema e uma fronteira clara (“a IA propõe; o store valida e persiste”), o modelo pode emitir campos, preços ou lugares que ninguém pediu — os “dados inventados”.

O resto deste documento elimina cada um desses riscos pela raiz: um modelo de dados normalizado, uma única fonte da verdade, um contexto que só aponta — não copia, e um ciclo de vida onde a viagem nasce real no servidor desde a primeira resposta do wizard.

01O que é uma viagem?

Uma Trip é a raiz de agregação: a unidade que tem dono, ciclo de vida e versão. Ela não contém cópias de hotéis, voos e passeios — ela os referencia por id. As entidades de catálogo (Hotel, Flight, Tour, Destination) vivem em suas próprias coleções e são imutáveis do ponto de vista da viagem. Isto é o que impede “Porto” de virar “Paris”: o dia aponta para um destinationId estável, não para uma palavra.

Entidades centrais

Trip — raiz de agregação // A única coisa que o usuário "possui". Tudo pendura aqui. Trip { id: TripId // id real do servidor, desde o draft ownerId: UserId title: string // "Portugal — Lisboa & Porto" status: TripStatus // draft | planning | active | completed | archived source: TripSource // wizard | manual | expert | template destinations: DestinationId[] // canônicos, ordenados dateRange: { start: ISODate, end: ISODate } | null travelers: Traveler[] budget: { currency: string, min: number, max: number, estimated: number } expertId: ExpertId | null days: TripDay[] // itinerário, ordenado por dayIndex bookings: BookingRef[] // hotéis/voos/passeios aplicados coverRef: ImageRef | null version: number // concorrência otimista — sobe a cada update createdAt: ISODateTime updatedAt: ISODateTime }
TripDay & ItineraryItem — o itinerário TripDay { id: TripDayId tripId: TripId dayIndex: number // 0-based, ordem canônica date: ISODate | null cityId: DestinationId // onde o dia acontece — nunca texto livre items: ItineraryItem[] // ordenados note: string | null } ItineraryItem { id: ItemId dayId: TripDayId slot: Slot // manha | tarde | noite kind: ItemKind // activity | meal | tour | transfer | checkin | flight refKind: RefKind | null // tour | flight | hotel — se houver entidade ligada refId: EntityId | null // id da entidade de catálogo title: string placeId: PlaceId | null durationMin: number | null status: ItemStatus // suggested | confirmed | booked confidence: number // 0..1 — quão segura a IA está locked: boolean // usuário fixou; IA não pode sobrescrever }

Dois campos resolvem a inconsistência dos roteiros: locked protege o que o usuário decidiu de qualquer regeneração da IA, e confidence deixa explícito o que é palpite versus o que é fato — a UI pode tratar os dois de forma diferente em vez de apresentar tudo como verdade.

Traveler — quem viaja Traveler { id: TravelerId kind: TravelerKind // adult | child | infant | pet name: string | null ageBand: string | null // "0-3" | "4-7" ... (crianças) petSize: string | null // pequeno | medio | grande documents: TravelerDoc[] // passaporte, autorização, vacina pet… }
Catálogo — Hotel · Flight · Tour (referenciados, imutáveis na Trip) Hotel { id: HotelId name: string cityId: DestinationId rating: number style: string // boutique | resort | … perks: string[] price: Money // por noite provider: string } Flight { id: FlightId segments: FlightSegment[] // from/to (airportId), carrier, no, depart/arrive, cabin price: Money miles: { program: string, amount: number } | null provider: string } Tour { id: TourId name: string cityId: DestinationId category: string durationMin: number price: Money provider: string }
Booking — a ponte entre desejo e reserva // Aplicar um hotel/voo/passeio ao roteiro cria um BookingRef. // É o que separa "sugerido" de "reservado de verdade". BookingRef { id: BookingId tripId: TripId refKind: RefKind // hotel | flight | tour refId: EntityId status: BookingStatus // none | held | booked | cancelled price: Money confirmationCode: string | null appliedToItemIds: ItemId[] // onde aparece no itinerário }

Dados de referência (canônicos)

Estas entidades existem antes de qualquer viagem e são compartilhadas por todas. São a defesa contra dados inventados: o frontend e a IA só podem referenciar ids que já existem aqui.

Destination · Place · Airport — vocabulário fechado Destination { id: DestinationId, city: string, region: string, country: string, geo: LatLng } Place { id: PlaceId, name: string, cityId: DestinationId, geo: LatLng, kind: string } Airport { id: AirportId, iata: string, cityId: DestinationId }
Por que isto mata o bug “Porto → Paris”

“Porto” deixa de ser uma string repetida em dez lugares e passa a ser { id: "dst_porto", city: "Porto", country: "PT" }. Um dia aponta para dst_porto. Para isso virar Paris, alguém teria que trocar o id — uma operação explícita, rastreável e validável contra a lista de destinos da viagem. A confusão silenciosa fica impossível.

Decisão recomendadaADR-04 · Dados

Lugares são entidades canônicas com id — nunca texto livre

Decisão
Destinos, cidades, aeroportos e lugares vivem em coleções de referência com id estável. Trip, TripDay e ItineraryItem referenciam esses ids; nenhuma string de lugar trafega no estado ou na API.
Justificativa
Causa raiz de “Porto → Paris”: lugar como string repetida e acoplada a seeds/chaves posicionais. Com id canônico, trocar de lugar vira uma operação explícita e validável.
Riscos
Exige um catálogo de referência mantido e um passo de resolução (texto do usuário → id) no wizard. Texto sem correspondência precisa de tratamento (sugerir/criar).
Não deve acontecer
Persistir nome de cidade como verdade; a IA emitir um lugar que não existe na tabela de referência; comparar lugares por string.
Impacto · Frontend
Telas exibem o nome resolvido a partir do id; selects/autocomplete devolvem DestinationId. Imagens deixam de depender de strings de “tone”.
Impacto · Backend
Expor catálogo de referência; validar todo id recebido; rejeitar patches da IA com ids inexistentes (400).
Impacto · Codex
Gerar tipos DestinationId/AirportId/PlaceId como branded types; proibir city: string em entidades de viagem; teste que falha se um item de itinerário guardar nome em vez de id.

02Qual é a fonte única da verdade?

Decisão: o backend é a fonte canônica; a Trip persistida é a entidade autoritativa. No cliente existe exatamente um cache normalizado dessa verdade — o Trip Store. Nenhum componente guarda cópia própria de dados de viagem. Telas lêem via selectors e escrevem via ações que passam pelo store e sincronizam com o servidor.

Por que o backend, e não a Trip em memória ou um contexto

  • Durabilidade & multi-dispositivo. A viagem precisa sobreviver a refresh, a outro device e ao expert humano editando junto. Só o servidor garante isso.
  • Versão = fim das regressões. Cada escrita carrega version. Se duas origens tentarem salvar em cima da mesma versão, o servidor rejeita (409) e o cliente re-sincroniza — em vez de uma sobrescrever a outra silenciosamente.
  • Fronteira para a IA. A IA propõe um patch; o servidor valida contra o schema e os ids de referência antes de persistir. Dado inventado não entra.
Decisão recomendadaADR-01 · Verdade

O servidor é canônico; o cliente tem um único cache espelho

Decisão
O backend é a fonte canônica da Trip. No cliente existe exatamente um cache normalizado (o Trip Store) que espelha o servidor. Telas lêem por selectors e escrevem por ações que sincronizam — nunca guardam cópia própria.
Justificativa
Todos os sintomas (Porto→Paris, conflitos, regressões, contexto perdido) são de múltiplas fontes da verdade. Durabilidade, multi-dispositivo e edição conjunta com o expert exigem o servidor. version por escrita elimina sobrescrita silenciosa.
Riscos
Latência percebida (mitigar com update otimista + rollback); complexidade de invalidação de cache; necessidade de reconciliar 409.
Não deve acontecer
Nenhuma tela mantém days/itinerary em useState; nenhum dado de viagem vive só na memória de um componente; nunca existirem “duas verdades” (catálogo + clone local).
Impacto · Frontend
Introduzir tripStore + selectors; remover os clones atuais (PlanScreen days/chat/prep); telas viram leitoras + emissoras de intenção.
Impacto · Backend
Trip como agregado com version; toda resposta devolve a Trip inteira; suportar If-Match e responder 409 em conflito.
Impacto · Codex
Gerar um único módulo de store + hooks de selector; regra de lint/teste que proíbe useState contendo dados de viagem; toda mutação obrigada a passar por action→API; teste que falha se um componente faz fetch direto.

03O que é o ActiveTripContext?

É a lente sobre a viagem em foco. Ele guarda a identidade (qual trip está aberta) e expõe leitura + ações para ela. Ele não é uma segunda cópia da viagem.

Objetivo
Saber qual é a trip ativa e dar às telas acesso ergonômico a ela sem prop-drilling.
Ciclo de vida
Nasce ao abrir/criar uma trip; persiste na navegação; é reidratado da URL (/trip/:id) no load; some no logout.

Responsabilidades

  • Manter activeTripId (só o id).
  • Expor selectors: useActiveTrip(), useTripDay(index), useItem(id) — que lêem do Trip Store.
  • Despachar intenções: addItem, moveItem, lockItem, applyHotel, applyFlight, applyTour — que viram mutations no store/servidor.
  • Expor status de sincronização: loading | ready | saving | error | stale.
O que o ActiveTripContext NÃO deve fazer

Não armazenar a viagem (só o id). Não buscar catálogo. Não transformar/mesclar dados. Não inventar defaults. Não duplicar o estado do wizard. Não conter lógica de apresentação. Se ele começar a guardar days, voltamos ao Risco 2.

Decisão recomendadaADR-03 · Contexto

ActiveTripContext guarda identidade, não dados

Decisão
O contexto carrega apenas activeTripId e expõe selectors + ações que operam sobre o Trip Store. É reidratado da URL (/trip/:id). Zero dados de viagem dentro dele.
Justificativa
Separar “qual trip está ativa” de “os dados da trip” evita a segunda cópia (a raiz do contexto perdido). Deep-link e refresh passam a ser triviais e seguros.
Riscos
Tentação de cachear a trip “para conveniência” dentro do provider — o que recria o problema. Precisa de disciplina/lint para conter.
Não deve acontecer
Guardar days; buscar catálogo; transformar/mesclar dados; duplicar o estado do wizard; conter lógica de apresentação.
Impacto · Frontend
Hooks useActiveTrip(), useTripDay(i), useItem(id); navegação por id; status de sync exposto (loading/ready/saving/error/stale).
Impacto · Backend
Nenhum direto (é client-side). Só requer GET /trips/:id idempotente para reidratar pela URL.
Impacto · Codex
Gerar o provider com superfície mínima (id + selectors + dispatch); teste que falha se o provider armazenar qualquer entidade de viagem; proibir props de dados de viagem atravessando o contexto.

04Como funciona o ciclo da viagem?

A viagem nasce real no servidor já na primeira resposta do wizard — como draft, com id verdadeiro e destino canônico. Nada de “objeto solto na memória que depois vira viagem”. Isso elimina a categoria inteira de bugs de “dado que existia na tela mas não no sistema”.

Decisão recomendadaADR-02 · Ciclo

A Trip nasce real (draft) no servidor desde a 1ª resposta do wizard

Decisão
A Trip é criada como draft no servidor já no início do wizard, com id real e destino canônico. Estados seguem uma máquina: draft → planning → active → completed → archived. A geração de dias pela IA é um passo separado sobre o draft.
Justificativa
Elimina o “objeto solto na memória que depois vira viagem” e a categoria de bugs de dado que existe na tela mas não no sistema. Permite retomar, compartilhar e sincronizar desde o primeiro passo.
Riscos
Drafts órfãos/abandonados (mitigar com TTL e limpeza); custo de criar cedo. Transições mal definidas geram escrita em estado errado.
Não deve acontecer
Criar viagem só no cliente; pular o draft; editar uma trip completed; a IA escrever em itens locked num generate.
Impacto · Frontend
Wizard chama POST /trips no início; permissões de edição derivam de trip.status; “Minhas Viagens” lista por status real.
Impacto · Backend
Criação de draft barata; transições de status validadas server-side; regra de “quem pode escrever” por status; limpeza de drafts.
Impacto · Codex
Implementar a máquina de estados como módulo único (fonte da verdade das transições); guarda central que rejeita mutação fora do status; gerar o fluxo wizard→draft→generate como passos explícitos.

05Decisões & simplificações

  1. Uma fonte da verdade: servidor canônico + um cache normalizado no cliente. Apague qualquer terceira cópia (estado local de tela que duplique dados de viagem).
  2. Tudo por id: destinos, lugares, aeroportos, hotéis, voos e passeios são entidades de referência. Itinerário aponta para ids, nunca para texto livre.
  3. Draft-first: a Trip existe no servidor desde a 1ª resposta do wizard. O cliente nunca “segura” uma viagem que o backend desconhece.
  4. Versão em toda escrita: concorrência otimista (version / If-Match) elimina regressões por sobrescrita.
  5. IA com fronteira: a IA emite patches validados contra schema + ids existentes. locked protege decisões do usuário; confidence separa palpite de fato.
  6. Context só aponta: ActiveTripContext carrega o id e expõe selectors/ações — nunca dados.
Resultado

Com isto, “Porto vira Paris”, “dados inventados” e “regressões” deixam de ser possíveis por construção — não por disciplina. O próximo documento (Component Contracts) traduz este modelo em props/eventos; o terceiro (API Contracts) o traduz em payloads compartilhados front↔back.
