Documento 02 — interface

Gaid Component Contracts V1

O que cada componente recebe, o que ele emite, e quais estados ele precisa saber desenhar. Todo componente é um apresentador puro: dado entra por props já resolvidas do store; intenção sai por callback. Nenhum componente busca, transforma ou inventa dado.

Forma · dados ↓ por props, intenções ↑ por eventos Proibido · fetch, defaults inventados, mutação direta Obrigatório · 4 estados — loading, empty, success, error

00Princípios transversais

  • Presenter puro. O componente não sabe de onde o dado veio. Recebe uma entidade já resolvida (ou seus ids + status) e a desenha.
  • Intenção, não mutação. Cliques não alteram dados — emitem eventos (onApply, onSelect, onChange) que o container traduz em ações do store.
  • Status explícito. Todo componente que depende de dado remoto recebe um status e desenha os 4 casos. “Sem dado” nunca é renderizado como dado vazio inventado.
  • Sem fabricação. Se um campo não veio, o componente mostra o estado de ausência — jamais um placeholder que pareça real (preço “R$ 0”, “Paris” por engano, etc).
Convenção de status — comum a todos LoadState = "loading" | "empty" | "success" | "error" // Todo card/lista recebe, no mínimo: { status: LoadState, data?: Entity, error?: UiError }
Decisão recomendadaADR-05 · Componentes

Todo componente é presenter puro: dados ↓ por props, intenções ↑ por eventos

Decisão
Componentes recebem entidades já resolvidas do store e emitem intenções (onApply, onSelect, onChange). Não buscam, não transformam, não mutam dado. O container traduz intenção em ação do store.
Justificativa
Acoplar fetch/lógica de dados no componente é como surgem dados inventados e estados divergentes. Presenter puro torna o componente testável, previsível e reutilizável.
Riscos
Mais boilerplate de container; props podem inflar (mitigar passando a entidade inteira + status, não 20 campos soltos).
Não deve acontecer
Componente fazer fetch; calcular preço/milhas; inventar default que pareça real (R$ 0, lugar errado); mutar o store diretamente.
Impacto · Frontend
Separar containers (ligam store) de presenters (desenham). Eventos sobem; dados descem. Reuso entre web e mobile.
Impacto · Backend
Nenhum direto — mas reforça que cálculos (preço, milhas, progresso) são responsabilidade do backend, entregues prontos.
Impacto · Codex
Gerar cada componente como função pura de (props) → UI; lint que proíbe fetch/efeitos de dados em presenters; cada componente entrega os 4 estados (ADR-06) ou o teste falha.

01GuidedWizard

Coleta a intenção de viagem em passos. Não cria a viagem sozinho: emite respostas; o container cria/atualiza o draft no servidor.

Inputs

PropTipoDescrição
stepsWizardStep[]Definição declarativa dos passos (id, pergunta, opções, regra de validação).
answersRecord<StepId, Answer>Respostas atuais (controlado pelo container — fonte da verdade fica fora).
stepIndexnumberPasso ativo.
statusLoadStateloading enquanto a IA gera após o último passo.

Outputs

EventoPayloadQuando
onAnswer{ stepId, answer }Usuário responde (opção ou texto livre).
onBack / onNext—Navegação entre passos.
onComplete{ answers }Último passo — container cria o draft.
onSkip—Pular onboarding/wizard.
loading · IA montando após último passo empty · nenhum passo respondido (estado inicial) success · passo renderizado, resposta aceita error · validação falha / geração falhou → permite retry
Não deve

Guardar as respostas como verdade interna, criar a Trip por conta própria, ou inferir destino a partir de texto sem confirmá-lo contra a lista de Destination.

06TripItinerary

A linha do tempo editável da viagem. É o componente onde o Risco 2 (clonar days para estado local) precisa morrer: ele lê do store via selectors e emite intenções de edição, sem manter cópia própria.

Inputs

PropTipoDescrição
tripIdTripIdIdentidade — os dias vêm do store por selector, não por prop clonada.
daysTripDay[]Já resolvidos do store (read-only para o componente).
statusLoadStateloading durante geração da IA; saving em mutações.
editablebooleanDepende de trip.status (não edita completed).

Outputs (intenções → mutations do store)

EventoPayloadVira
onAddItem{ dayId, slot, draft }mutation addItem
onMoveItem{ itemId, toDayId, toSlot }mutation moveItem
onEditItem{ itemId, patch }mutation updateItem
onRemoveItem{ itemId }mutation removeItem
onToggleLock{ itemId }protege da IA
loading · IA gerando os dias (skeleton da timeline) empty · roteiro sem itens → CTA “gerar / adicionar” success · dias e itens; locked/confidence visíveis error · geração ou save falhou → preserva o que existe + retry
Decisão

O TripItinerary nunca clona dados. Editar = emitir intenção → o store aplica (otimista) → o servidor confirma com nova version. Trocar de tela e voltar mostra exatamente o mesmo estado, porque só existe um. Fim do “contexto perdido”.

Decisão recomendadaADR-06 · Estados

Loading / empty / error / success são obrigatórios — não opcionais

Decisão
Todo componente que depende de dado remoto recebe um status: LoadState e desenha os quatro casos explicitamente. “Sem dado” é um estado projetado, nunca um dado vazio inventado.
Justificativa
A ausência de estados explícitos é o que faz a UI mostrar lixo durante carregamento/erro ou “fabricar” conteúdo. Tornar os 4 estados parte do contrato fecha essa porta.
Riscos
Mais superfície de design por componente; risco de estados inconsistentes entre telas (mitigar com primitivos compartilhados de skeleton/empty/error).
Não deve acontecer
Renderizar success com dados parciais; sumir com o componente em error (deve preservar e oferecer retry); tratar empty como error.
Impacto · Frontend
Criar primitivos <Skeleton/> <EmptyState/> <ErrorState/> reutilizados; status derivado do estado de query/store.
Impacto · Backend
Distinguir claramente vazio (200 + lista vazia) de erro (4xx/5xx + envelope de erro) para o cliente mapear o estado certo.
Impacto · Codex
Gerar cada componente com switch nos 4 estados; teste/snapshot por estado; falhar o build se faltar empty ou error em componente data-driven.
