Gaid Final Architecture Review V1

Revisão crítica dos Docs 01–04, decisão sobre os dois pontos em aberto (Trip vs TripDraft e estratégia de destinos), mapa de donos de estado e plano MVP em fases. Este documento é a base oficial — o que estiver travado aqui não se rediscute no meio da implementação.

Os seis problemas relatados (Porto→Paris, dados inventados, datas inferidas, wizard divergindo do roteiro, contexto conflitando com Trip, regressões) têm uma raiz comum: estado de viagem existindo em mais de um lugar, e lugares/datas trafegando como texto livre. As decisões abaixo eliminam a raiz — não tratam sintoma.

P1Parte 1 — Revisão crítica da arquitetura

1 · Fonte Única da Verdade

A decisão atual está correta. Mantém-se. Servidor canônico + um único cache normalizado no cliente (TripStore), com telas lendo por selectors e escrevendo por ações.

Validada — mantémADR-01 · revalidada

Servidor canônico; cliente com um cache espelho

Justificativa
É a única topologia em que “Porto→Paris”, dados inventados e regressões são impossíveis por construção, não por disciplina: existe um só lugar onde a viagem mora, e ele é durável.
Correção fina
Tornar explícito que LocalStorage e a busca de hotéis não são fontes de verdade — são, respectivamente, persistência do cache e estado de UI efêmero (ver §5).
Não deve acontecer
Tela com useState de dados de viagem; segundo espelho do servidor; “verdade” vivendo no Wizard ou no Context.

2 · ActiveTripContext

Responsabilidades corretas, desde que ele permaneça uma lente. O conflito relatado (“Context conflitou com Trip”) só acontece se ele guardar dados — o que está proibido.

Pode fazer
Guardar activeTripId; expor selectors (useActiveTrip, useTripDay); despachar ações (applyHotel, patch); expor status de sync; reidratar da URL.
Não pode fazer
Guardar a Trip ou days; buscar catálogo; transformar/mesclar dados; duplicar o estado do Wizard; conter lógica de UI.

Ciclo de vida: nasce ao abrir/criar uma Trip → persiste durante a navegação → é reidratado de /trip/:id no load → é limpo no logout. Ele nunca “possui” a viagem; só aponta para ela.

3 · Trip vs TripDraft

A preocupação é legítima: Wizard → Trip direto gera viagens-lixo se o usuário desistir no meio. Mas criar uma entidade TripDraft separada dobra o modelo (duas tabelas, duas APIs, migração draft→trip) — overengineering para o MVP.

CritérioA · Wizard cria TripB · Wizard cria TripDraft
SimplicidadeAlta — uma entidadeBaixa — duas entidades + promoção
UXBoa, mas pode poluir “Minhas Viagens”Boa — lixo nunca aparece
ImplementaçãoMínimaDobrada (modelo, API, migração)
RiscoViagens incompletas visíveisDivergência draft↔trip (mais um par de fontes a sincronizar)
EscalabilidadeBoa se o status resolver a visibilidadeBoa, porém mais cara
Decisão recomendadaADR-08 · Draft

Uma só entidade Trip, com status: draft — o melhor dos dois

Decisão
Adotar a mecânica da Opção A (uma entidade) com a semântica da Opção B (rascunho gateado). O Wizard cria a Trip já como status: "draft"; “Minhas Viagens” lista apenas planning | active | completed. Confirmar promove draft → planning.
Justificativa
Evita viagens-lixo visíveis sem introduzir uma segunda entidade e uma segunda fonte a sincronizar (que recriaria o problema “wizard divergiu do roteiro”). Um campo resolve o que uma tabela inteira resolveria — mais barato e mais seguro.
Riscos
Drafts órfãos acumulando. Mitigação: TTL/limpeza server-side e “1 draft ativo por usuário por vez” no MVP.
Não deve acontecer
Criar tabela/entidade TripDraft; o Wizard manter um rascunho próprio em paralelo à Trip; draft aparecer em “Minhas Viagens”.
Impacto · Frontend
Wizard chama createTrip no início e edita a mesma Trip; listas filtram por status; “confirmar” chama promote.
Impacto · Backend
Status na Trip; criação de draft barata; TTL de draft; transição draft→planning validada.
Impacto · Codex
Não gerar entidade TripDraft. Gerar filtro de visibilidade por status como única regra; teste: draft não aparece em Minhas Viagens; promover torna visível.

4 · Destination Strategy

Os dois extremos são ruins: só lista cadastrada é restritiva (“Toscana” não existe → usuário travado); texto livre puro é a porta de “Porto→Paris” e datas/lugares inventados. A resposta não é escolher um — é a interface certa com o dado certo para o MVP.

Decisão recomendadaADR-09 · Destinos

Destination Resolver (interface) sobre lista curada (dado do MVP)

Decisão
Adotar a interface da Opção B — um resolveDestination(texto) → DestinationId — porém, no MVP, lastreado por uma lista curada (Opção A). Toda escolha do usuário vira um DestinationId antes de tocar a Trip.
Justificativa
A Trip nunca vê texto livre (mata Porto→Paris), mas o Resolver isola a estratégia: trocar “lista curada” por “geocoding/serviço externo” depois não muda nenhum chamador. Decisão reversível sem refatoração.
Riscos
Texto sem correspondência na lista. Mitigação MVP: autocomplete só sugere ids existentes; “não encontrei” explícito em vez de adivinhar.
Não deve acontecer
A Trip armazenar “Toscana” como string; o Resolver “chutar” um id por similaridade frágil; a IA inventar um destino fora do catálogo.
Impacto · Frontend
Campo de destino = autocomplete que devolve DestinationId; nunca envia texto para a Trip.
Impacto · Backend
Endpoint/serviço de resolução; validar todo DestinationId; recusar ids inexistentes.
Impacto · Codex
Gerar resolveDestination como contrato estável; implementação MVP = lookup na lista; teste: entrada sem match retorna “não resolvido”, nunca um id aproximado.

5 · Estados duplicados — mapa de donos

Risco restante neutralizado declarando, para cada estado, quem cria, quem atualiza, quem consome e se é ou não fonte de verdade. Só a Trip é verdade; o resto é cache, ponteiro ou UI efêmera.

Regra única

Se um dado descreve a viagem, ele vive na Trip e em nenhum outro lugar. Se um dado é “como o usuário chegou até aqui” (respostas do wizard, query de busca, filtros), ele é UI efêmera e morre ao concluir a ação. Não existe terceira categoria.

P2Parte 2 — MVP Implementation Plan (fases)

Cada fase é entregável e verificável isolada. Fases 3–6 reusam exatamente o padrão provado na Fase 2 (buscar → card → aplicar → roteiro reflete) — sem novas decisões de arquitetura.

Fase 1 — Fundação

Escopo: Trip · TripStore · ActiveTripContext · Wizard · Minhas Viagens.

Objetivo: uma viagem persistente funcionando.

Critério de aceite

Criar viagem → fechar o app → reabrir → a viagem continua existindo (reidratada do servidor/persistência, sem recriar dados). Draft não aparece em Minhas Viagens; promovido aparece.

Fase 2 — Hotéis

Escopo: Hotel Search · HotelCard · Aplicar hotel ao roteiro.

Critério de aceite

Buscar hotel → receber resultados (4 estados) → aplicar → roteiro atualiza corretamente, sem regressões. Sair e voltar mantém o item aplicado.

Fase 3 — Voos (escopo mínimo)

  • searchFlights(fromAirportId, toAirportId, datas, pax) → FlightCard (4 estados).
  • applyFlight(tripId, flightId, dayId?) → insere item flight no dia da partida.
  • Aceite: aplicar voo reflete no roteiro sem afetar o hotel já aplicado.

Fase 4 — Passeios (escopo mínimo)

  • searchTours(cityId, date) → TourCard (4 estados).
  • applyTour(tripId, tourId, dayId, slot) → anexa item tour ao dia/slot.
  • Aceite: passeio aparece no dia correto; demais itens intactos.

Fase 5 — Experts (escopo mínimo)

  • listExperts(region) (diretório read-only) + assignExpert(tripId, expertId).
  • Aceite: atribuir grava expertId na Trip e reflete no roteiro. Sem canal/chat humano.

Fase 6 — Assinaturas (escopo mínimo)

  • getPlans() · getSubscription() · setSubscription(planId).
  • Aceite: trocar de plano atualiza a Subscription e o tier exibido. Sem cobrança/billing real.

Onde a regressão é mais provável

  • TripItinerary — era o epicentro dos clones; primeiro lugar a auditar a cada PR.
  • Aplicar item — risco de duplicar itens/bookings ao aplicar duas vezes (sem idempotency no MVP, garantir guarda no store).
  • Reidratação pós-reload — Trip ativa precisa voltar pela URL/sessão sem recriar dados.
  • Telas legadas em mock (Wallet/Miles) — não devem acoplar ao TripStore nem quebrar quando os mocks de viagem saírem.

Decisões a tomar ANTES de voltar ao Codex

  1. Trip vs TripDraft → travado: uma Trip com status: draft (ADR-08).
  2. Destinos → travado: Resolver sobre lista curada (ADR-09).
  3. Formato de id → definir convenção (ex.: dst_*, trip_*, htl_*) e branded types.
  4. Onde mora o catálogo de hotéis no MVP → atrás do tripApi, nunca montado na tela.
  5. Política de dias → days derivados do dateRange (vazios) na criação; itens só via aplicar.
  6. Regra de promoção → o que confirma draft → planning (ação explícita do usuário).

✓Decisões travadas (base da sprint)

O que está fechado
  1. Arquitetura validada: servidor canônico + um cache (TripStore) + Context só com id.
  2. Fonte única da verdade: a Trip. Tudo mais é cache, ponteiro ou UI efêmera.
  3. Trip vs TripDraft: uma Trip com status: draft — sem entidade separada.
  4. Destinos: Destination Resolver com lista curada; Trip só vê DestinationId.
  5. Plano MVP: 6 fases; Fase 1 (persistência) e Fase 2 (hotel) provam o padrão; 3–6 clonam.
  6. Riscos: mapeados, com mitigação e os pontos de auditoria por PR definidos.

Com isto a próxima sprint começa sem decisões de arquitetura em aberto. O que o Codex implementar deve respeitar estas travas — qualquer desvio é bug de arquitetura, não escolha de implementação.
