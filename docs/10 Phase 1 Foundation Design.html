Documento 10 — Fase 1 · desenho da fundação (spec para implementação)

Foundation Design

A especificação da nova fundação — Trip, TripTemplate, TripStore, ActiveTripContext, tripApi, contracts e projeções — ancorada nos contratos da Fase 0 (Doc 08) e na ordem da Fase 0 Exec (Doc 09). Detalhada para o Codex implementar sem tomar decisões estruturais: o que cada módulo é, o que expõe, o que é proibido, e como mapeia para as formas que a UI já espera.

Formato · schemas + assinaturas declarativas (não implementação) Restrição · UI/UX/navegação intactas Meta · spec autossuficiente p/ Codex

00Princípios da fundação

  • Modelo canônico + projeções. Existe uma Trip canônica. As telas nunca a consomem direto: consomem projeções (view-models) que reproduzem exatamente as formas da Fase 0.
  • Dado desce por seleção, intenção sobe por ação. Telas leem via selectors; mudanças são ações no store — nunca mutação local.
  • Uma fronteira de I/O. Todo dado entra pelo tripApi. Nenhum módulo de UI importa catálogo/fixtures.
  • Identidade por id. Toda entidade e relação usa id canônico. Strings de exibição continuam existindo, mas nunca são chave.
  • A apresentação é imutável. Nada nesta fundação pede mudança de UI. Se algo exigiria, é bug de design — não de implementação.

02contracts — tipos, ids, enums, mapeamentos

O vocabulário canônico. Tudo abaixo é declarativo: define forma e regra, não comportamento.

Ids & enums

Ids tipados (branded) — prefixos fixos TripId = "trip_…" TemplateId = "tpl_…" // catálogo (hoje "routes") ExpertId = "exp_…" HotelId / FlightId / TourId / PlanId = "htl_… / flt_… / tour_… / plan_…" DayId / ItemId = "day_… / itm_…"
Enums canônicos TripStatus = "draft" | "idea" | "planning" | "active" | "completed" | "archived" Slot = "manha" | "tarde" | "noite" // UI exibe "manhã/tarde/noite" ItemStatus = "suggested" | "confirmed" | "booked"

Regra de mapeamento status ↔ rótulo da UI (TRAVADA)

A UI exibe e filtra por rótulos em português (mapState() no TripsScreen). A projeção deve emitir exatamente estes rótulos. O Codex não escolhe nomes novos.

Regra de formatação (TRAVADA)

A UI consome strings já formatadas e às vezes as parseia. A fundação guarda valor estruturado e entrega a string idêntica à de hoje. Formatos exatos a reproduzir:

CampoValor canônicoString que a projeção entrega (idêntica à atual)
price{ currency:'R$', amount:4820 }"R$ 4.820" (+ priceValue:4820 cru)
dates (resumo){ start, end }"12–22 out · 2026"
dates (detalhe){ start, end }"12–22 outubro"
durminutos"3 h" / "90 min"
Por que guardar os dois

String para a UI não mudar; valor cru para ordenar/calcular sem parseInt(price.replace(...)). A UI continua usando a string; o valor cru fica disponível para quando quisermos remover o parsing — sem pressa.

Entidades de catálogo (formas da Fase 0, com id adicionado)

Catálogo — campos idênticos ao Doc 08 + ids canônicos Hotel { id, name, city, rating, nights, price, perk, tone, tag } Flight { id, from, to, dep, arr, airline, flight, stops, dur, price, miles, best, tone } Tour { id, name, city, dur, price, host, hostExpertId, tone } Expert { id, portrait, name, region, regions:[], trips, routes, rating, responseMin, years, tone, specs:[] } Plan { id, name, tag, highlight, desc, price, period, features:[], cta } Starter{ id, label, hint, tone }
Única adição além da Fase 0

hostExpertId (Tour) e expert→expertId nas relações: substituem o cruzamento por nome (risco 6). Os campos de exibição por nome (host, expert) permanecem para a UI não mudar.

03Trip — o modelo canônico (fonte única)

Uma única estrutura. Dela derivam todas as projeções (resumo e detalhe). Não há "duas viagens".

Trip (canônica) Trip { id: TripId status: TripStatus title: string blurb: string | null destinationLabel: string // "Portugal — Lisboa & Porto" cities: string[] // exibição; ids canônicos quando houver dates: { start: ISODate, end: ISODate } | null nights: number | null travelers: number // contagem (UI mostra "N viajantes") budget: Money | null progress: number // 0..100 cover: string // tom: warm|cool|sage|coral|ink coverSeed: string | null coverLabel: string | null expertId: ExpertId | null templateId: TemplateId | null // origem, se semeada de um template days: TripDay[] insights: { kind: string, text: string }[] prep?: PrepGroup[] // fluxos kids/dog (opcional) createdAt: ISODateTime updatedAt: ISODateTime } TripDay { id: DayId, d: number, date: string, city: string, flight?: boolean, items: Item[] } Item { id: ItemId, slot: Slot, title, place, dur, tag, vibe, conf: boolean, refKind?: "hotel"|"flight"|"tour", refId?: EntityId, status?: ItemStatus }
Invariantes (o Codex deve garantir)
  • Toda Trip tem id real desde a criação (sem objeto solto sem id).
  • days[].items[].slot ∈ {manha,tarde,noite}; a UI traduz para "manhã/tarde/noite".
  • Campos ausentes são null explícito — nunca inventados.
  • Edição só via ação do store; a Trip nunca é clonada para estado de tela.

04TripTemplate — o catálogo (read-only)

O que hoje são mockData.routes + routeDetails: roteiros editoriais/inspiração. Imutável e compartilhado; semeia uma Trip, nunca é referenciado vivo em runtime (mata o dataKey).

TripTemplate TripTemplate { id: TemplateId title: string category: string days: number from: string // "R$ 38k" (string de exibição) expert: string // nome p/ exibição expertId: ExpertId | null tone: string detail?: TemplateDetail // itinerário expandido (hoje routeDetails[id]) } // Criar viagem a partir de um template = COPIAR para uma Trip nova: createTripFromTemplate(templateId) → Trip // status:"planning"|"draft"; templateId preenchido
Decisão (estrutural — travada)

Template e Trip são entidades distintas. A Trip recebe uma cópia dos dados do template no momento da criação. Mudar o catálogo nunca altera viagens existentes. Acabou o "a viagem é um objeto do catálogo resolvido por string".

05Projeções / view-models — a ponte para a UI atual

Cada projeção produz exatamente a forma que a tela já consome (Doc 08). É a peça que garante paridade visual. O Codex implementa estes mapeamentos — não inventa formas.

toTripSummary(trip) — para TripsScreen e Home

TripSummary (forma do card de Minhas Viagens) TripSummary { id, title, dates: string, // "12–22 out · 2026" state: string, // rótulo PT via mapa travado (§02) travelers: number, tone: string, // = trip.cover cover: string, // rótulo curto p/ SmartImg ("Lisboa") progress: number, hasItinerary: boolean // substitui o check mockData[dataKey] }

toTripDetail(trip) — para PlanScreen e Home (viagem ativa)

TripDetail (forma do roteiro) — campos idênticos ao Doc 08 TripDetail { id, title, blurb, dates: string, // "12–22 outubro" nights, travelers, budget: string, // "R$ 24–28k" status: string, // rótulo PT (mesma família do state) cover, coverSeed, coverLabel, progress, expert, days: [ { d, date, city, flight?, items:[ { t, title, place, dur, tag, vibe, conf } ] } ], insights: [ { kind, text } ] } // item.t = "manhã"|"tarde"|"noite" ← derivado de Item.slot

Regra de ouro das projeções

A saída de cada projeção é comparada campo a campo contra o objeto que a tela recebe hoje (baseline da Fase 0). Igual → corte aprovado. Diferente → conserta a projeção, nunca a tela.

06TripStore — cache único, selectors, ações

O coração da fundação. Único lugar onde dados de viagem moram no cliente. Resolve os 4 estados internamente (sem expô-los na UI).

Estado interno (normalizado) TripStoreState { byId: { [TripId]: Trip } // cache único allIds: TripId[] status: { [chave]: "loading"|"success"|"empty"|"error" } // por consulta error: { [chave]: UiError | null } }
Selectors (leitura — devolvem PROJEÇÕES, nunca a Trip crua) selectTripSummaries() → TripSummary[] selectTripDetail(id) → TripDetail | null selectActiveTripDetail() → usa ActiveTripContext.activeTripId selectStatus(chave) → "loading"|"success"|"empty"|"error"
Ações (escrita — única forma de mudar uma viagem) loadTrips() // → tripApi.listTrips loadTrip(id) // → tripApi.getTrip createTrip(input) / createTripFromTemplate(templateId) applyHotel(tripId, hotelId, nights) applyFlight(tripId, flightId, dayId?) applyTour(tripId, tourId, dayId, slot) patchItinerary(tripId, ops[]) // add/move/update/remove/setLock setProgress(tripId, n) // Toda ação chama o tripApi, recebe a Trip atualizada e substitui no cache.
Proibições (o que mata regressão)
  • Nenhum componente recebe a Trip crua — só projeções.
  • Nenhuma tela mantém useState com dados de viagem (fim do clone do PlanScreen).
  • Ação sempre devolve a Trip inteira; o cache é substituído, não mesclado à mão.

07ActiveTripContext — só o id

ActiveTripContext ActiveTripContext { activeTripId: TripId | null setActiveTripId(id) } // NÃO guarda Trip, days, nem qualquer dado. Só o ponteiro. // Telas que precisam da viagem ativa: selectActiveTripDetail() no store.
PodeNão pode
Guardar activeTripId; trocar de viagem ativa; reidratar o id (URL/sessão)Guardar a Trip ou days; buscar dados; transformar/mesclar; conter lógica de UI
Transição de posse (vindo do account)

Hoje activeTripId e trips[] vivem no account. Na fundação: activeTripId → ActiveTripContext; trips[] → TripStore. O account fica só com sessão/usuário/onboarding.

08tripApi — a fronteira (seam)

Única porta de dados. Hoje devolve fixtures (repackaging do mockData); amanhã, fetch. As assinaturas e formatos de retorno não mudam entre os dois — é isso que mantém a UI intacta na virada do backend.

tripApi — assinaturas (retornam SEMPRE formas canônicas de contracts) // Viagens listTrips() → Trip[] // drafts/archived filtrados na projeção getTrip(id) → Trip | null createTrip(input) → Trip createTripFromTemplate(templateId)→ Trip patchTrip(id, ops[]) → Trip applyHotel/applyFlight/applyTour(…) → Trip // Catálogo / busca searchHotels(q) → Hotel[] searchFlights(q) → Flight[] searchTours(q) → Tour[] listTemplates(q?) → TripTemplate[] getTemplate(id) → TripTemplate listExperts(q?) → Expert[] listPlans() → Plan[] // Config do wizard in-chat (Home) getWizardDef(flow) → WizardDef // disney|kids|dog getGenSteps(flow) → GenStep[] getStarters() → Starter[]
Como o backend entra (sem tocar UI)

Cada método troca o corpo (fixture → fetch('/api/v1/…')) mantendo a assinatura. Doc 03 (API Contracts) já define os endpoints correspondentes. Telas, store e projeções não percebem a troca.

09Fluxo de dados

Leitura (ex.: abrir o roteiro)

read path Tela(PlanScreen) → selectActiveTripDetail() → ActiveTripContext.activeTripId → TripStore.byId[id] (se ausente: loadTrip → tripApi.getTrip → cache) → toTripDetail(trip) → props idênticas às de hoje

Escrita (ex.: aplicar hotel)

write path Tela → store.applyHotel(tripId, hotelId, nights) → tripApi.applyHotel(...) → Trip atualizada → store substitui byId[tripId] → selectors re-emitem projeções → UI reflete (sem clone, sem merge manual)

10Decisões travadas (o Codex não decide)

Estrutura fixada nesta spec
  1. Uma Trip canônica + projeções TripSummary/TripDetail; nunca duas entidades de viagem.
  2. Template ≠ Trip; criar viagem copia do template (sem dataKey vivo).
  3. TripStore é o único cache; selectors devolvem projeções; ações são a única escrita.
  4. ActiveTripContext guarda só activeTripId.
  5. tripApi é a única fronteira de I/O; assinaturas fixas (Doc 03).
  6. Mapa status↔rótulo e formatos de string são os da §02 — exatos, para a UI não mudar.
  7. Relações por id (expertId etc.); strings de nome só para exibição.
  8. Sem clones de dados de viagem em estado de componente.
Deixado em aberto de propósito (parâmetro, não estrutura)

Persistência concreta do cache (memória/localStorage), origem das fixtures (arquivo único vs. por entidade) e detalhes de formatação de datas localizadas são parâmetros de implementação — não mudam a arquitetura e podem ser decididos no código, desde que respeitem os contratos acima.

✓Definição de pronto (Fase 1 · desenho)

Esta spec está completa quando…
  1. Cada módulo tem responsabilidade única, dependências unidirecionais e proibições explícitas. ✓
  2. A Trip canônica cobre todos os campos que as projeções da Fase 0 exigem. ✓
  3. Cada tela tem uma projeção que reproduz sua forma atual campo a campo. ✓
  4. O tripApi lista todas as operações que store/telas precisam, com retornos canônicos. ✓
  5. Mapeamentos sensíveis (status↔rótulo, formatos) estão travados — o Codex não improvisa. ✓

Com isto, a implementação pode começar pela ordem do Doc 09 (Planos → buscas → catálogo → Minhas Viagens → Home → Roteiro), construindo a fundação isolada e cortando tela por tela atrás de flag. Próximo passo possível (quando você quiser): a Fase 1.5 — o "kit de paridade" por tela (checklist de campos a comparar antes de ligar cada flag). Sem implementação.
