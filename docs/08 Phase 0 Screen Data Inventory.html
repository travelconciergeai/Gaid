Inventário de Dados por Tela

As "formas esperadas" de cada tela, extraídas do código atual — não de suposição. Para cada tela: o que consome, de onde vem hoje, de onde virá na nova fundação, o contrato que espera, e o que muda para trocar a origem sem alterar a UI. É a base que blinda a paridade visual antes de qualquer corte.

Fonte da evidência · src/screens/*, src/mockData.jsx, src/account.jsx Regra · UI/UX/navegação intactas Saída · contratos por tela + veredito de reaproveitamento

00Método & evidência

Cada linha abaixo foi verificada lendo o arquivo correspondente: quais campos a tela acessa, em qual variável, vinda de qual fonte. Onde cito um campo (ex.: liveTrip.coverSeed), ele aparece literalmente no JSX hoje. O objetivo é que o tradutor (view-model) da migração reproduza exatamente essas formas.

01As duas fontes de dados de hoje

Toda tela lê de um (ou ambos) destes dois lugares — nunca de uma API:

mockData (catálogo estático)
Objeto único em src/mockData.jsx. Chaves: user, starters, trip, cards, milesPrograms, benefits, experts, routes, flights, hotels, tours, trips[], maldivasTrip, japaoTrip, plans, chatSeed, quickActions, itemAlternatives, disneyTrip, dogTrip, disneyWizard, kidsWizard, dogWizard, genSteps*, routeDetails.
account (estado do usuário)
useAccount() em src/account.jsx: authed, needsOnboarding, mode, profile, user{...}, trips[], cards[], milesPrograms[], benefits[], activeTripId + ações (login, addTrip, setActiveTripId…). No modo demo, é semeado a partir do mockData.
A indireção que conecta as duas (e quebra)

Em App.jsx: tripFor(id) acha a meta em acct.trips ou mockData.trips, lê meta.dataKey e resolve mockData[meta.dataKey] para o itinerário completo. Resumo e detalhe da mesma viagem são objetos diferentes, com campos diferentes (ver §Achados).

02Veredito: a UI pode mesmo ser 100% reaproveitada?

Validado com ressalvasEvidência

Sim — a apresentação é reaproveitável 100%, desde que o tradutor entregue as formas atuais

Confirmado
Nenhuma tela faz fetch ou lógica de servidor. Todas leem objetos JS já prontos. Trocar a origem por um view-model que devolva o mesmo objeto não exige mudar o JSX.
Ressalva 1
Existem duas formas por viagem (resumo vs. detalhe), com chaves divergentes (state vs status). O tradutor precisa expor duas projeções: TripSummary e TripDetail.
Ressalva 2
"Guided Wizard" não é uma tela — é um fluxo in-chat dentro da Home (disneyWizard/kidsWizard/dogWizard + passos de geração). Reaproveitar = manter esse fluxo; a fundação só fornece a definição e cria a Trip.
Ressalva 3
Vários campos são strings já formatadas (price: 'R$ 4.820', dates: '12–22 out · 2026') e a UI às vezes as parseia (Voos ordena por parseInt(price.replace(/\D/g,''))). O tradutor deve devolver as mesmas strings (idealmente + um campo numérico cru), senão a UI muda.
Conclusão
A afirmação se sustenta. O risco não está na UI, e sim em o tradutor reproduzir fielmente cada forma — exatamente o que este inventário especifica.

04Achados que afetam a migração

Duas formas por viagem. Resumo usa state; detalhe usa status + blurb/nights/coverLabel.Expor duas projeções da mesma Trip: TripSummary e TripDetail. Mapear status ↔ state com os mesmos rótulos.

account semeado do mock. Demo copia mockData.* para o account.account mantém sessão/usuário; trips[]/activeTripId migram para o TripStore na Fase 4.
Saída da Fase 0

Os contratos por tela acima são a especificação do tradutor: para cada tela, o view-model deve produzir exatamente estas formas. Com isto, dá para construir a fundação (Fase 1) e o tradutor (Fase 2) e, a cada corte, comparar a saída contra estes contratos — garantindo paridade visual antes de ligar qualquer tela. Nenhuma mudança de UI, UX ou navegação é necessária para a migração.
